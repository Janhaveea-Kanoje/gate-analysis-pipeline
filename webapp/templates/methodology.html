The core design rule: AI reads, rules decide

Every gate in this pipeline follows one strict rule: a large language model is only ever allowed to read messy text and turn it into structured data (e.g. "what form and dose does this label describe?"). It is never allowed to make the actual pass/fail decision. That decision always comes from plain, fixed, deterministic code.

This matters because language models are known to occasionally get precise numbers wrong — a real risk for a health-adjacent decision. Keeping AI restricted to reading, and rules restricted to deciding, means every decision this tool makes can be traced back to an explicit, checkable threshold, not a model's best guess.

Where each gate gets its evidence

GateSource
Gate 0 — FormulationA 101-ingredient evidence file (forms, safe dose ranges) built from the research team's data
Gate 1 — RegulatoryThe live UK Food Standards Agency Novel Food register — a real government database, checked in real time
Gate 2 — QualityNo open dataset of batch-specific lab certificates exists, and the research team's own search found none — the biggest remaining gap. The gate is built and exercised only with hypothetical inputs.
Gate 3 — Brand IntegrityLive UK Companies House (company verification) + live FSA Food Alerts (recall history)
Gate 4 — MedicalThe same evidence file as Gate 0, used as a stand-in for a full clinical-study-dose database that doesn't exist yet

The headline finding

The one gate that needed no AI reading step — a plain database lookup (Gate 1) — scored highest, ahead of both gates that rely on an LLM reading label text (Gates 0 and 4), even after multiple rounds of fixing the reading step. Gate 3's lookups were limited by data coverage and a heavily skewed ground truth, so they don't test this comparison. The evidence supports keeping the AI to reading and leaving every decision to a plain rule — not a claim that lookups always win.
Section 01 · Outcomes

Verdict states

A product clearing all five gates receives a tier — never a numeric score, and never partial credit for a gate it didn't clear. In the current build the outcome is Tier 1 or Tier 3; Tier 2 is part of the design but cannot be reached yet (explained in its card).

Tier 1

All 5 gates pass, using a Superior-tier form at the upper end of the evidence-based dose range, with premium (ISO 17025) testing. Requires expert panel consensus before publication — this pipeline flags it, it does not auto-publish it.

Tier 2 · not reachable yet

Designed for a Superior form at the top of the dose range without premium (ISO 17025) testing. In the current build it cannot occur: Gate 2 already requires an ISO 17025 lab to pass, so every product that reaches the tier step has premium testing. Recorded as a known limitation.

Tier 3

All 5 gates pass, but either the form is not Superior or the dose is not at the top of the range — a baseline, adequate product. Every Acceptable-form product that clears all gates lands here.

Tier 0

Failed at least one gate. Evaluation stops at the first failing gate — a product is never assessed against later gates once it has failed an earlier one.

Section 02 · The corpus

How the ground truth was built

01
Manual review
The researcher applied the same five-gate criteria this pipeline now applies automatically to real UK products (1,754 in the Gate 0 sheet, after removing 104 summary rows) — before any of this automation existed. A research-team collaborator then independently re-labelled every product, and the two sets of labels were reconciled to a final consensus.
02
Evidence base
Forms and safe-dose ranges for 101 ingredients were compiled from the research team's clinical evidence sources.
03
Extraction
A large language model reads each product's free-text label and turns it into structured form and dose data — it never decides pass or fail.
04
Rule engine
Fixed, deterministic thresholds compare the extracted data against the evidence base to reach a verdict.
05
Comparison
The automated verdict is checked against the original manual review, using Cohen's kappa to correct for chance agreement rather than raw percentage alone.

This matters for how the accuracy numbers on the previous page should be read: they measure agreement with a consensus label set from two independent reviewers — stronger than a single reviewer, but short of the independent expert panel the framework requires for its highest-confidence tier (Tier 1, above). The specific gap: the two reviewers' original, pre-reconciliation labels were not kept, so an inter-rater agreement figure (kappa) for the ground truth itself cannot be reported. A fresh expert-panel labelling round, with the original labels retained, is named as future work.

Section 03 · Honesty

What this pipeline doesn't claim

This automated pipeline is a research prototype, evaluated against real data, not a certified consumer product. Stated plainly:

  • It is not a medical endorsement, and not a guarantee of individual safety for any person or product.
  • Gate 2 has no empirical result. No open dataset of batch-specific laboratory certificates exists anywhere — this is stated as a data gap, not glossed over as "in progress."
  • Gate 4 uses a safety-threshold proxy, not an implementation of its actual defined requirement (matching a product's dose against the specific clinical study it cites) — that real per-study dose database does not exist yet.
  • The evidence file is a strong draft, not a verified source. Its 101 entries have no machine-extractable citations; key bioavailability claims (magnesium, zinc, curcumin, omega-3, iron) were checked against the literature — several turned out to be contested — but not every row. One form (Prenatal Vitamin) appears as both Acceptable and Reject in the source file and is provisionally treated as Acceptable pending the research team's confirmation. New evidence or a corrected entry can change a prior result.
  • Every live API this pipeline depends on (FSA Novel Food, FSA Food Alerts, UK Companies House) is a third-party government service outside this project's control — several real integration errors were caught and corrected during this work, illustrating that such dependencies need ongoing verification, not a one-time integration effort.
